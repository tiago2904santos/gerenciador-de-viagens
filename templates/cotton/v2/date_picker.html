DELEGA ao partial global `cotton/ui/forms/date_picker.html`, que é o único ponto de verdade da marcação do calendário — há um teste de contrato para isso (`test_calendar_markup_exists_only_in_the_global_partial`), e ele me pegou: a primeira versão deste componente recriou o markup, o que reintroduzia exatamente a divergência que o partial existe para impedir. O v2 acrescenta só o invólucro `.date-field`, para a folha `static/css/v2/date-picker.css` vestir o campo sem alcançar as telas legadas. `start_field`/`end_field` são os `BoundField` do formulário. Passá-los faz o calendário escrever nos campos ocultos que o Django vai ler no POST — sem eles o componente é só um seletor de tela, que mostra a data e não salva nada. `start_hidden_name`/`end_hidden_name` são a alternativa para quem NÃO tem formulário: o filtro de uma lista, que manda os valores por querystring. Um ou outro, nunca os dois. Três modos, e o editor de roteiro usa os três (2026-08-17): - `range` — o intervalo, que é o caso de termos e ordens de serviço; - `single` — UMA data, com campo visível e oculto separados (`single_input_id`/`single_hidden_id`). É o de cada trecho e o do retorno; - `multi` — várias datas de uma vez, com confirmação (`show_confirm`) e repetição permitida (`allow_repeat_dates`). É o "preencher datas" que enche a pilha de trechos em sequência. `trecho_date` marca o papel da data no card do trecho (`saida`/`chegada`) — o editor procura por ele para saber onde escrever. Os três eram só do componente legado até esta data, e é por isso que o editor de roteiro era a última tela de formulário presa a ele. Nenhum markup de calendário foi copiado: o que mudou aqui é a lista de parâmetros repassados ao partial global. O JS é o `js/components/date-picker.js`, achado pelo partial. {% endcomment %}
